correct API signatures, code patterns, and QoS settings before writing code.

## CRITICAL: DynamicData vs @idl.struct

**If you need to subscribe to a topic published by another process, use DynamicData — NOT @idl.struct.**

`@idl.struct` subscribers receive **ZERO samples** from `DynamicData` publishers. This is an RTI DDS type system incompatibility. Since you don't control the publisher, always use DynamicData:

```python
# CORRECT — works with any publisher:
hello_type = dds.StructType('HelloWorld')
hello_type.add_member(dds.Member('message', dds.StringType(256)))
hello_type.add_member(dds.Member('count', dds.Int32Type()))
topic = dds.DynamicData.Topic(participant, 'HelloWorld', hello_type)
reader = dds.DynamicData.DataReader(participant.implicit_subscriber, topic)

# WRONG — receives 0 samples if publisher uses DynamicData:
# @idl.struct class MyType: ...
# topic = dds.Topic(participant, 'TopicName', MyType)
# reader = dds.DataReader(subscriber, topic)
```

**For GUID discovery tasks**: Use `get_pattern('discovery_publication_guid')` and `get_pattern('discovery_subscription_guid')` — these are COMPLETE working scripts. Copy the code directly, adapt the topic name and fields, and you're done. Do NOT try to access builtin topics via `Subscriber.lookup_datareader()` or `DataReader.find_by_topic()` — those APIs don't exist on generic classes.

## Tips
- Always look up the API before using RTI DDS classes you haven't used before
- Use get_pattern for complete working examples of common DDS patterns
- For discovery/GUID tasks: use `get_pattern('dynamicdata_subscriber')` — never @idl.struct
- Use get_qos_recipe when configuring QoS for specific scenarios
- Use diagnose_error when you encounter errors to get specific fixes
